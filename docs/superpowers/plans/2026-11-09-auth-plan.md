# Auth Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Email-code sign-in with rotating refresh tokens, display-name onboarding, and the frontend session state that spec 2's builds catalog will build on.

**Architecture:** A new `api/app/auth/` package holds small building-block modules (`codes`, `tokens`, `rate_limit`, `email`, `cookies`, `deps`) underneath a thin router. All state lives in three new MySQL tables. On the frontend, `src/lib/api.ts` gains refresh-and-retry, session state lives in shared code at `src/hooks/auth/`, and the screens live in `src/features/auth/`.

**Tech Stack:** FastAPI, SQLAlchemy 2 (sync, PyMySQL), MySQL 8, PyJWT, httpx, pytest; React 19, TypeScript, react-router, shadcn.

**Spec:** `docs/superpowers/specs/2026-11-09-auth-design.md`

**Who writes what:** Omar writes the models, schemas, building-block modules, routes and middleware. Claude writes the migration, fixtures and every test (tests first: Claude's test step comes before Omar's code step), and reviews each task. The frontend is paired.

**After every API task:** from `api/`, run `uv run ruff check . && uv run ruff format --check . && uv run pytest`, ask Claude to review, then commit.
**After every frontend task:** run `pnpm exec tsc -b && pnpm lint`, ask Claude to review, then commit.

**Branches:** a stack of six branches, one per PR, cut in order starting from `auth-design`: `auth-schema` → `auth-primitives` → `auth-sign-in` → `auth-sessions` → `auth-frontend-session` → `auth-frontend-screens`. Each PR stays under 500 lines, excluding pure deletions.

**Staging:** the working tree has unrelated `.agents/` deletions. Stage files by name, never with `git add -A` or `git add .`.

## Global Constraints

- Code lifetime 10 min; attempt cap 5; cooldown 60 s per email; 5 codes/hour per email; 20 codes/hour per IP; `login_codes` rows deleted after 24 h.
- Access JWT: HS256, claims `sub` (user ID as a string) and `exp`, lifetime 15 min, decoded with `algorithms=["HS256"]` only.
- Refresh token: 256 random bits, stored as hex SHA-256, lifetime 30 days, grace window 30 s.
- Code hash: hex HMAC-SHA256 keyed with `CODE_HMAC_SECRET`.
- Cookies: `access_token` on `Path=/api`, Max-Age 900; `refresh_token` on `Path=/api/auth`, Max-Age 2592000; both `HttpOnly`, `SameSite=Lax`, with `Secure` when `COOKIE_SECURE`.
- Display name pattern: `^[A-Za-z0-9_]{3,30}$`, unique ignoring case (`utf8mb4_0900_ai_ci`).
- Every timestamp in app code is naive UTC, taken from `get_now()`. Never use MySQL `NOW()` or `datetime.now()` directly.
- No process-memory state: no module-level caches, counters or dicts in the API.
- Error copy, exactly: `"Invalid or expired code"`, `"Couldn't send the code, try again"`, `"Display name taken"`, `"Origin not allowed"`.
- Never edit an applied migration. New schema goes in `016_auth.sql`.

## Review Focus

These five input classes and failure modes are implied by the spec but missed by its test table. Each has a test added to the task named.

1. **Different email spelling between the two steps.** A user requests a code with `" Me@Example.COM "` and verifies with `"me@example.com"`; it must work. → Task 3.2 `test_verify_matches_email_case_insensitively`.
2. **Code pasted with spaces, or with a leading zero.** `" 012345 "` must verify, because the schema strips whitespace and the code stays a string. → Task 3.2 `test_verify_accepts_padded_code_with_whitespace`.
3. **A returning user.** Verifying as a user who already has a display name must return it, so the frontend skips `/welcome`. → Task 3.2 `test_verify_returns_existing_display_name`.
4. **Cookies that never actually clear.** A cookie is only deleted if the deleting `Set-Cookie` uses the same `Path`, so a mismatch leaves users logged in after logout. → Task 2.4 `test_clear_auth_cookies_uses_matching_paths`.
5. **Page load with an expired access cookie.** `GET /auth/me` must go through refresh-and-retry, so the frontend skips refresh only for `/auth/code`, `/auth/verify`, `/auth/refresh` and `/auth/logout`. → Task 5.1, step "Manual check".
